**Owner rulings, 2026-10-21 (answers written back as spec):**
1. All four items ship together in one release, v4.1.0. They are not split into v4.1.0 and v4.2.0, even
   though C+D take longer than A+B.
2. The remap reuses the existing `smoke_path`/`smoke_status` inputs. It does not add
   `probe_path`/`expected_status`. When `retarget_from` is set, `smoke_path` is required and an empty
   `smoke_status` means 200. Consumer A is told about this change from the name in the agreed design.
3. The remap reuses the existing `certificate_timeout_seconds` (default 1800 = 30 min) and adds no
   `cert_timeout_minutes`. On a remap run, a timeout fails the run. The docs tell remap callers to set
   3600 if they want the 60 minutes the ruling suggested.
4. `deploy-cloud-run`'s `image` input accepts only a digest reference (`…@sha256:<64 hex>`). A tag
   reference is refused.
5. (Asked during the build, 2026-10-21.) The SHA-pin gate (`scripts/check_pinned_actions.py`)
   allows this repo's own composite actions to be pinned to an exact release tag:
   `Just-Git-Dev/reusable-workflows/actions/<name>@vX.Y.Z`. Nothing looser is allowed: a partial
   tag, a branch or a pre-release tag still fails, as does a tag on any other repo or on our own
   reusable workflows. The reason is that a wrapper workflow cannot SHA-pin an action that first
   exists in its own release commit.
   `stamp_version.py` rewrites that tag at release.
6. (Asked during the build, 2026-10-21.) A re-run with `retarget_from` set does not change the
   mapping when the hostname is already on `service`. It still waits strictly for the
   certificate and still probes, so a slow certificate or a bad status fails the run. This
   catches a remap that half-failed earlier.
7. (Asked during the build, 2026-10-21.) The concurrency reminder is a `::notice::` when the
   action is called by our own wrapper workflow, which declares the group itself. That workflow
   passes an input saying so. A direct caller of the action still gets the `::warning::`.
8–9. Rulings on fleet work outside this repo. They are recorded in the fleet's private tracker,
   not here.

## A — `bootstrap-cf-service` retarget (v4.1.0)

Spec = the owner ruling in RW `TODO.md:"map AND remap a Cloud Run domain"`, implemented as written
except where rulings 2/3 decide.

**Inputs (new):** only `retarget_from` (string, default '' = refuse exactly as today). The probe
uses the existing `smoke_path`/`smoke_status` (ruling 2) and the cert wait uses the existing
`certificate_timeout_seconds` (ruling 3). The Validate step (:179) refuses:
`retarget_from` with `mode: proxied` (proxied has no GCP mapping — not in the ruling, inferred,
documented); `retarget_from` without `smoke_path`; `retarget_from` == `service`.
In the steps below, "probe path" means `smoke_path` and "expected status" means `smoke_status || 200`.

**Steps:**
1. New `Pre-flight the retarget` step before Converge (only when `retarget_from` set): target
   service exists, latest revision Ready, serves 100% traffic, its run.app URL answers the probe
   path with the expected status (`curl -o /dev/null -w '%{http_code}'`). Refuse with nothing
   deleted otherwise.
2. Converge step (:252): when `current == retarget_from` → (dry run: print plan: current routeName,
   target readiness, delete+create) else record `T_DELETE`, `domain-mappings delete`, `create`.
   `current == service` stays a no-op (safe re-run). Any other `current` refuses as today.
3. Cert wait (:390): on a retarget run, poll every 30s up to the timeout and **fail** on timeout
   (today it only warns — unchanged for non-retarget runs).
4. Probe `https://<host><probe path>`; on retarget, failure fails the run; record `T_OK`.
5. Summary: outage window (`T_DELETE` → `T_OK`), and on any failure after delete, the exact
   map-back command (`gcloud beta run domain-mappings delete … && … create --service=<retarget_from>`).
6. CAA: look up the zone's CAA records via the CF API already in use; if CAA exists and does not
   allow `pki.goog`, emit a warning.

**IAM:** docs/bootstrap-cf-service.md IAM table (:75-83) gains `run.domainmappings.delete`,
`run.services.get`, and a documented custom role (no `run.admin`).

## B — `deploy-cloud-run` prebuilt `image` (v4.1.0)

**Input:** `image` (string, default '' = build as today). Per ruling 4 it must be a digest
ref `<region>-docker.pkg.dev/…/<name>@sha256:<64 hex>` — a tag can move between the gate's test and
this deploy; a digest cannot.

**Behaviour when set:**
- `Resolve tag + image ref` (:247): `image` output = the input; tag still resolved (it drives
  checkout, the Deployment record and `require_semver`).
- Refuse `image` + `build_only` (contradiction). `also_tag_latest`, build inputs ignored, with a
  notice listing which.
- Skip `Configure docker`, `setup-buildx`, `Build & push` (`if: inputs.image == ''`).
- New `Verify prebuilt image` step: `gcloud artifacts docker images describe "$IMAGE"` — fails
  if the digest is not in GAR (the releaser SA already has GAR access); emits the digest.
- Keep checkout (commit SHA for `jgd_commit` label + forward-only guard + env_file), env render,
  bundle pin, Deploy, Deployment record, manifest, summary — unchanged.
- Manifest `IMAGE_DIGEST` (:658): `steps.build.outputs.digest || steps.verify.outputs.digest`.

**Not doing:** comparing the image's OCI revision label with the checkout SHA (images from other
build systems may not carry it) — the caller passes the same tag for both; noted in docs.
Precedent: `promote-image.yml` deploys a digest but skips env/bundle/labels/manifest — B is the full
path; the doc says which to use when.

## C + D — composite actions (v4.1.0, ruling 1)

**Pattern:** the composite action is the single source of truth; logic moves into scripts beside
it (`actions/sync-bundle-key/*.sh`, `actions/rotate-worker-signing-secret/*.sh`), as
`check-release-gate`/`refresh-api-spec` already do, so `make shellcheck` covers them (inline
action `run:` bodies are NOT linted, Makefile:93-112). The existing reusable workflow becomes a thin
wrapper calling `Just-Git-Dev/reusable-workflows/actions/<name>@vX.Y.Z` (ref swept by
`scripts/stamp_version.py:42-48`) — a `./` ref would resolve to the CALLER's repo (TODO.md:702).
Workflow keeps permissions/concurrency/timeout; the action documents what the caller's job must
declare.

**C specifics:** environment secrets reach the action as an input the caller sets in its own
`environment:` job: `secrets_json: ${{ toJSON(secrets) }}` (values stay masked — registered
secrets). Caller MUST declare `concurrency: bundle-write-<proj>-<secret>` — the cross-workflow
mutual exclusion asserted by `tests/run_concurrency_tests.py`; the doc gives the exact block, and
the action prints a warning naming it. Branch-policy guard needs `actions: read` in the caller job.
WIF unaffected: bindings are `attribute.repository` = caller repo either way (agent finding; no
doc conditions on `job_workflow_ref`).

**D specifics:** same pattern; while moving the bodies, fix `${{ steps.gen.outputs.new_secret }}`
interpolated straight into `run:` (rotate-worker-signing-secret.yml:256,260,365) → pass via `env:`
(script-injection/log-exposure hygiene; ships with an RCA).

**Test harness:** `extract_step` (run_step_tests.py:59) reads `jobs.*.steps`; add an
`extract_action_step` for `runs.steps`, and point `run_sync_v4_tests.py` at the scripts.
